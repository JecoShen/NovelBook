# novel-workflow-11-analyze：质量分析

本 skill 是写作流程中的**独立质量关卡**。它不修改任何正文，只产出结构化的分析报告。所有发现以严重度分级，附带证据和修复建议，但不自动执行修复——修复决定权在用户。

## 与其他流程的关系

```
... → 09-chapter-writing → 11-analyze → 10-revision（如需修复）→ 11-analyze（复查）
```

- **10-revision** 是修复工具，负责改正文。
- **11-analyze** 是诊断工具，只发现问题、不修复。
- 分析报告中标记为 `CRITICAL` / `HIGH` 的问题，用户可选择进入 10-revision 修复。
- 修复完成后可再次运行 11-analyze 做复查（只复检上次标记的问题）。

## 边界

不要在本流程中：

- 修改任何正文、lorebook、World Engine 数据。
- 替用户决定哪些问题必须修。
- 对 `LOW` 级别问题要求修复——它们只是建议。
- 在分析报告中使用模糊评价（"写得不错""感觉不太好"）——每条发现必须有具体证据。

## 工作方式

用 task_create 建立检查清单，逐维度扫描。每个维度独立检查，最后汇总。

建议 task checklist：

1. 确定分析范围（单章 / 连续章节 / 整卷 / 全书）。
2. 读取目标正文和关联上下文。
3. 逐维度执行检查（共 7 个维度）。
4. 汇总发现，按严重度排序。
5. 产出结构化分析报告。
6. 汇报给用户，等待用户决定修复范围。

如果用户只要求检查某几个维度（如"只看伏笔"），只执行对应维度。

## 分析维度

### 维度 1：情节一致性

检查章节之间、章节与 World Engine 状态之间是否自洽。

**检查方法**：

1. 读取目标章节正文，提取关键事件（角色行动、位置变化、物品得失、信息披露）。
2. 查询 World Engine 相关 subject 在章节时间范围内的切面。
3. 对比正文描述与 World Engine 记录是否一致。

**检查项**：
- 角色位置：正文描述的位置是否与 World Engine 记录一致？
- 状态变化：受伤、治疗、升级等是否衔接上一章？
- 物品持有：角色手中的物品是否与前一章结束时一致？
- 时间流逝：章节之间的时间间隔是否合理？（例如上一章结尾是傍晚，本章开头是清晨，中间发生了什么？）
- 能力一致性：角色使用的能力是否已在 lorebook 或之前的剧情中交代？（如果突然使用新能力且无 backstory slice，标记）

**严重度判定**：
- `CRITICAL`：正文与 World Engine 矛盾，且会影响后续剧情走向（如角色位置错误、关键物品凭空出现）。
- `HIGH`：正文与 World Engine 矛盾，但影响范围有限（如次要角色的状态不一致）。
- `MEDIUM`：正文内部前后矛盾（如第 2 段说左手受伤，第 10 段用左手拿东西）。
- `LOW`：时间流逝感不够自然，但不影响剧情逻辑。

### 维度 2：角色弧完整度

检查目标范围内每个主要角色是否有清晰的行为动机和变化轨迹。

**检查方法**：

1. 从 World Engine 和 lorebook 获取目标角色的当前状态、目标、误信念。
2. 阅读目标章节，追踪该角色的每个决策点。
3. 判断每个决策是否可以从角色设定（性格、目标、恐惧、误信念、已知信息）中推导。

**检查项**：
- 角色是否做了"不符合人设"的选择？（如果是，是否有充分的剧情解释？）
- 角色的外部目标和内在需求是否有推进？
- 角色是否在被动反应而非主动选择？（连续 2 章以上完全被动 → 标记）
- 角色的情绪变化是否有铺垫？（突然的情绪爆发而无前文铺垫 → 标记）
- 配角是否沦为"功能性工具人"？（只提供信息或帮助，没有自己的动机和选择 → 标记）

**严重度判定**：
- `CRITICAL`：主角做出了与核心设定（性格/目标/误信念）完全矛盾的关键选择，且无解释。
- `HIGH`：重要配角的动机缺失或不一致，影响剧情可信度。
- `MEDIUM`：角色连续被动，缺乏主动选择时刻。
- `LOW`：情绪转折略快，但尚在可接受范围。

### 维度 3：伏笔兑现率

利用 Plot Promise 系统检查伏笔的埋设、推进和兑现状态。

**检查方法**：

1. 用 `get_story_promise` 查询当前项目中所有 Promise。
2. 按状态分类：`open`（已埋未兑现）、`in_progress`（推进中）、`resolved`（已兑现）、`abandoned`（已废弃）。
3. 检查目标章节范围内的 beats：是否有新的埋设、推进或兑现。
4. 识别需要关注的 Promise。

**检查项**：
- 是否有长期 `open` 且无近期推进的 Promise？（超过 10 章无任何 beat → 标记"可能遗忘"）
- 新埋的伏笔是否都有明确的兑现计划或至少方向？
- 兑现的伏笔是否在埋设时有足够的铺垫？（突然兑现而无前文线索 → 标记"伪伏笔"）
- 废弃的 Promise 是否有明确的废弃原因记录？

**严重度判定**：
- `CRITICAL`：核心主线的 Promise 长期无推进（可能影响全书结构）。
- `HIGH`：重要支线的 Promise 超过约定范围无推进。
- `MEDIUM`：伏笔兑现时缺乏足够的前文铺垫（可补）。
- `LOW`：次要伏笔可考虑废弃但未标记。

### 维度 4：LLM 写作痕迹

使用 llmlint 工具扫描正文中的 AI 写作痕迹。

**检查方法**：

1. 对目标章节文件运行 `llmlint check <文件路径>`。
2. 汇总 error 和 warning 级别的问题。
3. 人工审阅 warning 项，判断是否误报。

**检查项**（llmlint 覆盖 + 人工补充）：
- Filler phrases：空洞的过渡句、无信息量的描述。
- 机械句式：重复的句式结构（连续多句"他……了""她……着"）。
- 抽象说理：角色用议论代替行动、用内心独白代替场景展示。
- 过度总结：章末的"从此……""这一夜……"式 AI 惯用收尾。
- 情感标签：用"很愤怒""非常悲伤"代替行动和细节展示。

**严重度判定**：
- `HIGH`：llmlint error 级别问题。
- `MEDIUM`：llmlint warning 级别问题（经人工确认）。
- `LOW`：llmlint warning 但经人工判断为合理用法。

### 维度 5：信息边界越界

检查叙事是否让角色知道了不该知道的信息。

**检查方法**：

1. 从 brief/PRD 和 World Engine 提取每个出场角色的知识边界（谁知道什么、谁不知道什么）。
2. 逐角色检查其对话、内心独白、行为反应。
3. 判断是否出现越界。

**检查项**：
- 角色是否做出了只有"上帝视角"才能做出的判断？
- 角色的内心独白是否包含了他在当前时间点不可能知道的信息？
- 角色对话中是否泄露了只有读者和作者知道的秘密？
- 第一人称/第三人称有限视角下，叙述者是否超越了视角限制？

**严重度判定**：
- `CRITICAL`：主角知道了会影响核心剧情走向的秘密，而该秘密尚未在剧情中披露给他。
- `HIGH`：配角越界知道了不应知道的信息。
- `MEDIUM`：叙述者的描述略微超出当前视角角色的感知范围（如"他没有注意到的角落里……"）。
- `LOW`：可能越界但可解释为合理的推测或巧合。

### 维度 6：节奏与张力

检查目标章节的节奏是否合理，张力是否有起伏。

**检查方法**：

1. 阅读目标章节，按场景/片段标注节奏类型（紧张/舒缓/过渡/高潮）。
2. 绘制简化的节奏曲线。
3. 检查是否符合该章节类型的基本节奏预期。

**检查项**：
- 是否连续多个场景保持同一节奏而无变化？（连续紧张导致麻木，连续舒缓导致无聊）
- 高潮场景是否足够紧凑？（字数过多、描写过于细致导致张力消散 → 标记）
- 过渡场景是否过长？（超过本章 20% 字数的纯过渡 → 标记）
- 章末是否有钩子？（以日常/平静收尾且无悬念 → 标记）
- 爽点/释放是否在读者期待的位置出现？

**严重度判定**：
- `HIGH`：连续多章缺乏节奏变化或所有章末无钩子。
- `MEDIUM`：单章内节奏问题（如高潮拖沓、过渡过长）。
- `LOW`：节奏细微可调但整体可接受。

### 维度 7：成功标准达成度

对照 story-concept 中定义的 SMART 成功标准，检查当前进度。

**检查方法**：

1. 读取 `lorebook/note/story-concept/` 中的成功标准段。
2. 逐条对照目标章节范围，判断是否达成。
3. 对标记为 `[核心需求]` 的标准，未达成即为 `CRITICAL`。

**检查项**：
- 每条 `[核心需求]` 标准是否在当前范围内被满足？
- 每条 `[需要澄清]` 标准是否已经有了答案或仍悬而未决？
- 是否有隐性的质量偏离（没有明确标准但明显不符合故事气质）？

**严重度判定**：
- `CRITICAL`：`[核心需求]` 标准未达成。
- `HIGH`：成功标准持续多章未达成且有恶化趋势。
- `MEDIUM`：单章内某项标准未达成。
- `LOW`：`[可选特性]` 有机会实现但未尝试。

## 输出格式

分析报告使用结构化格式。不要输出完整正文复述——只输出发现的问题。

```markdown
# 质量分析报告

**分析范围**：[章节范围或卷号]
**分析时间**：[时间]
**分析维度**：[实际执行的维度列表]

## 总览

| 严重度 | 数量 |
|--------|------|
| CRITICAL | X |
| HIGH | X |
| MEDIUM | X |
| LOW | X |

## CRITICAL

### [C1] [维度] 问题简述
- **位置**：`文件路径` 第 N 段 / 行号
- **证据**：引用正文中的具体内容或 World Engine 数据
- **影响**：如果不修复会导致什么后果
- **建议**：修复方向（不自动执行）

## HIGH
（同上格式）

## MEDIUM
（同上格式）

## LOW
（可选，简要列表即可）

## 成功标准追踪

| 标准 | 标记 | 状态 | 备注 |
|------|------|------|------|
| ... | 核心需求 | ✅/❌/⚠️ | ... |

## 伏笔概览

| Promise | 状态 | 最近推进 | 备注 |
|---------|------|---------|------|
| ... | open/in_progress/resolved | 第X章 | ... |

## 下一步建议

- 建议优先修复：C1, H2, ...
- 建议在下一轮写作中关注：...
- 建议进入 10-revision 修复范围：...
```

## 收尾

完成后只输出：

- 分析范围和执行的维度。
- 各严重度的问题数量。
- 是否需要进入 10-revision 修复。
- 修复优先级建议。

不要把完整报告内容重复粘贴到聊天中——报告已写入文件。

默认将报告保存到当前小说 workspace：
- `lorebook/note/analysis-reports/YYYY-MM-DD-chapter-XX-XX.md`

如果该目录不存在，先创建 `lorebook/note/analysis-reports/` 目录节点。

## 完成标准

- 所有选定维度已执行检查。
- 每条发现都有具体证据（正文引用或 World Engine 数据）。
- 每条发现都有严重度判定和修复建议。
- 报告已保存到 workspace。
- 已向用户汇报关键发现和修复优先级。
- 正文、lorebook、World Engine 未被修改。
